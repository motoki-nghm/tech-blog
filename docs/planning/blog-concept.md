# ブログコンセプト企画書

- 作成日: 2026-07-07
- 担当: 企画(クラピカ)
- ステータス: 確定(オーナー合意済み)

## 1. 目的

フリーランスとしての営業先(発注者)からの信頼獲得。
「AIを活用したアプリを実際に作り、課題を解決できる人物」であることを、実績ベースの記事で証明する。

- 最上位目的: ポートフォリオとして技術力と発信力を示す(CLAUDE.md 準拠)
- 本ブログにおける具体化: 営業先が読んで「この人に頼みたい」と判断できる材料を揃える

## 2. 想定読者

| 優先度 | 読者像 | 知りたいこと |
|---|---|---|
| 主 | 発注者(非エンジニア〜半技術者) | この人に頼むと自分の課題がどう解決するか。実績と進め方 |
| 従 | 営業先の技術担当者 | 本当に作れるのか。技術判断の妥当性、コードの質 |

### 読者設定から導かれる執筆方針

- 記事の主役は技術ではなく「課題 → 判断 → 成果」のストーリー
- 専門用語は絞り、半技術者が読み切れる平易さを基準にする
- ただし技術担当者の検証に耐える技術記事も一定数用意する

## 3. コンテンツ方針

**「AIアプリ製作実録」を主軸、「AI活用の実践知見」を従とするハイブリッド。**

- 主軸(実録): 実際に開発したAIアプリごとの事例・製作記。実績の直接証明
- 従(知見): 製作記から派生する横断的な知見(AI協働の進め方、技術選定の考え方など)。発信力と検索流入を担う
- 構成比の目安: **事例・解決ストーリー 7 : 技術解説 3**

### 選定理由

- 実際に作ったアプリという一次情報があるため、実録は競合と差別化できる
- アプリ数が少ない弱点は、1アプリ複数記事のシリーズ設計と派生知見記事で補う
- 汎用テックブログ化は「何の人か」がぼやけるため採らない

## 4. シリーズ設計: 1アプリ4記事の分割軸

1アプリにつき最低4本の記事を標準セットとする。

| # | 記事タイプ | 内容 | 主な読者 |
|---|---|---|---|
| 1 | 事例サマリー | なぜ作ったか・何が解決したか・成果。シリーズの入口 | 発注者 |
| 2 | 意思決定編 | 技術選定・AI活用範囲の判断とその理由 | 発注者・技術担当者 |
| 3 | AI協働の実践編 | Claude をどう使い、どこで人が判断したか | 発注者・技術担当者 |
| 4 | 技術深掘り編 | 実装の要点1テーマに絞った解説 | 技術担当者 |

- 各記事は単体で読めるように書き、シリーズ内は相互リンクする
- 深掘りテーマが複数あるアプリは 4 を複数本に増やしてよい

## 5. 制作フロー

オーナーの執筆時間が取れないため、関与を最小化する。

**制約: オーナーの関与は「素材提供 15分」+「最終確認 10分」の2点のみ。**

| 手順 | 担当 | 内容 |
|---|---|---|
| 1. 企画 | クラピカ | バックログから次の記事を選定し、構成案を作成 |
| 2. 素材提供 | オーナー | アプリの背景・スクリーンショット・リポジトリ等を渡す(箇条書き可) |
| 3. 執筆 | ゴン | 構成案と素材をもとに MDX 記事を執筆 |
| 4. 校正 | ビスケ | 校正・ファクトチェック・公開前チェック |
| 5. 公開判断 | オーナー | 最終確認して公開可否を決める |

## 6. 公開ポリシー

- オーナーは**公開可能な素材のみ**を提供する(選別はオーナーが行う)
- 提供された素材は実名・実コードを含め**全公開可**として扱う
- 執筆側は提供素材の範囲外の情報(未提供の顧客名・数値など)を推測で書かない

## 7. サイト要件への示唆(実装・デザインへの引き継ぎ事項)

- **実績/事例ページ**: 事例サマリー記事を一覧できる導線をトップに置く(営業先の最初の着地点)
- **タグ/カテゴリ設計**: 「事例」「AI協働」「技術解説」を軸にした分類。アプリ名タグでシリーズを束ねる
- **プロフィール/問い合わせ導線**: 営業目的のため、記事から連絡手段への導線を必ず設ける
- 詳細要件はキルア(実装)・ヒソカ(デザイン)への引き継ぎ時に別途整理する
