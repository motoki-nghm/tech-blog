このブログは、6体のAIエージェントと役割を分担しながら立ち上げた。企画・実装・デザイン・執筆・レビュー・運用——本来は専門の異なる工程を、Claude を土台にした「担当の違うAI」に分け、対話しながら一つずつ進めている。

この記事は、その進め方をこのサイト自身を題材に記録したものだ。ソフトウェア開発の外注を検討している方に向けて、「AIを使う開発が実際どう進むのか」「どこまでをAIに任せ、どこで人が判断するのか」を、具体的な工程に沿って示す。専門知識がなくても読み通せるように書いた。技術的な判断の詳細は後半にまとめたので、開発担当の方はそちらも確認してほしい。

## 題材はこのブログ自身

作ったのは、ポートフォリオ用のテックブログ——つまり、いま読んでいるこのサイトそのものだ。開発したアプリの事例や、その裏側にある判断を公開し、「この人に仕事を任せられそうか」を実績で判断してもらうことを目的にしている。

最初の題材にこのサイト自身を選んだのには理由がある。外部から素材をもらわなくても、リポジトリ(ソースコードや設定を管理する保管場所)の中身がそのまま一次資料になるからだ。企画書も、デザインの決定記録も、実際の作業履歴も、すべてこの製作記の裏付けとして残っている。作り方をそのまま見せられる題材、というわけだ。

## 課題 — ひとりで、限られた時間で立ち上げる

ブログを一本立ち上げるだけでも、必要な作業は幅広い。誰に何を届けるかの企画、サイトの実装、デザイン、記事の執筆、公開後の集客——どれも性質の違う仕事だ。ひとりで全部を担うと、どこかで手が回らなくなり、品質が落ちる。

さらにこのプロジェクトには、はっきりした時間の制約があった。オーナー(発注者にあたる本人)が使える時間は、素材提供と最終確認でごく短時間のみ。企画方針として、この関与を最小化することが最初から決められていた。

つまり課題はこうだ。**限られた人の時間で、幅広い工程の品質を落とさずに立ち上げる。** これをどう解くかが最初の判断になった。

## 判断 — 6人のAIエージェントに役割を分けた

採った方針は、1体のAIに全部を丸投げするのではなく、**工程ごとに担当の違うAIを用意する**というものだ。それぞれに専門の役割と視点を持たせ、対話しながら進める。

役割の名前には HUNTER×HUNTER のキャラクターを当てた。担当と守備範囲は次のとおり。

| 担当 | 役割 | 主な守備範囲 |
|---|---|---|
| クラピカ | 企画・戦略 | コンセプト設計、記事企画、情報設計、要件整理 |
| キルア | 実装 | セットアップ、機能実装、ビルド・デプロイ設定 |
| ヒソカ | デザイン | 配色・タイポグラフィ、レイアウト、CSS設計 |
| ゴン | 記事執筆 | 記事の執筆・リライト・構成の肉付け |
| ビスケ | レビュー・品質 | コードレビュー、記事校正、公開前チェック |
| レオリオ | SEO・運用 | SEO、OGP、計測、パフォーマンス、集客 |

分ける利点は、責任範囲がはっきりすることだ。企画の相談はクラピカ、実装はキルア、というように窓口が決まっているので、それぞれの担当と会話を続ければ文脈が積み上がっていく。ひとつのやり取りに複数の判断が混ざらず、議論が散らからない。

### なぜ「キャラクター」を与えたのか

キャラクターは飾りではなく、視点を固定するための仕組みだ。

たとえばレビュー担当のビスケには、「動作確認されているか」「誤字や事実誤認はないか」「対象読者と結論が冒頭で示されているか」といった観点があらかじめ与えられている。実装担当のキルアには、「不要な依存を増やさない」「必ず自分で動作確認する」という原則がある。役割ごとに判断基準を決めておくことで、毎回ゼロから指示しなくても、その担当が見るべき点をぶれずに見てくれる。

もうひとつ、口調や性格を固定しておくと、どの担当と話しているかが一目でわかる。作業の切り替えがはっきりし、対話が進めやすくなる。

なお、キャラクターの口調はあくまで対話のときだけのものだ。実際の成果物——コードや記事本文、この文章——には持ち込まないことを明確なルールにしている。読み手に向けた文章は、中立でプロフェッショナルな文体で書く。

## 制作の流れ — 企画から執筆まで

ここからは、実際にどの順で作ってきたかを追う。作業履歴(Git のコミット記録)がそのまま残っているので、順序は事実に基づいている。

大きな流れはこうだ。

```text
1. 企画      クラピカ … コンセプトと記事バックログ
2. 実装      キルア  … Astro + MDX の土台
3. 公開準備  キルア  … Vercel でゼロコンフィグ公開
4. デザイン  ヒソカ  … ブルーグレーのデザインシステム
5. 執筆      ゴン    … この記事(いまここ)
```

### 企画:誰に何を届けるか決める

最初にクラピカが、ブログのコンセプトと記事の計画を固めた。

決めたのは、主な読者を「開発を発注する側の人」に置くこと。そのうえで、記事の主役を技術そのものではなく「課題 → 判断 → 成果」のストーリーにすること。専門用語は絞り、半分技術がわかる程度の読者でも読み切れる平易さを基準にすること。この方針がなければ、記事は書き手の都合で専門的になりすぎてしまう。最初に読者を定めたことが、以降すべての工程の土台になった。

### 実装:Astro + MDX の土台

次にキルアが、サイトの土台を組んだ。採用したのは **Astro**(表示が速い静的サイト向けのフレームワーク)と **MDX**(通常の文章に部品を埋め込める記事フォーマット)だ。

この段階で、記事一覧・タグ・記事ページといった骨格が用意された。記事はすべてリポジトリ内のファイルとして管理する構成にしている。技術選定の理由は後半で改めて説明する。

### 公開準備:Vercel でゼロコンフィグ

続いてキルアが、公開の準備を整えた。ホスティング(サイトを配信するサービス)には **Vercel** を選び、専用の追加設定なしで公開できる状態にしてある。サイトはあらかじめHTMLとして書き出す静的な作りなので、余計な部品を足さずに配信できる。

### デザイン:信頼を伝えるブルーグレー

見た目はヒソカが担当した。基調色はブルーグレー(青みがかった落ち着いた灰色)。硬すぎず、かといって砕けすぎない中間の色で、発注者に向けた「読みやすさ」と「誠実な第一印象」の両立を狙っている。

ここでも派手さより実利を優先している。デザインを効率化する外部ツールはあえて入れず、標準のCSSだけで組んだ。読み込みが重くなる装飾フォントも初期は見送った。表示の速さそのものが信頼につながる、という判断だ。ダークモード(暗い配色)は、閲覧環境に合わせて自動で切り替わるようにしている。

### 執筆:いま読んでいるこの記事

そして最後に、執筆担当のゴンがこの記事を書いた。あなたがいま読んでいるこの文章が、製作フローの現在地だ。企画で定めた読者と方針に沿って、これまでの工程を素材にしてまとめている。

## 人が判断した部分、AIに任せた部分

この進め方で一番伝えたいのは、**AIに任せた部分と、人が判断した部分がはっきり分かれている**という点だ。

AIが担ったのは、案を複数出すこと、方針に沿って形にすること、決められた観点で確認すること——手を動かす部分と、たたき台を作る部分だ。

一方で、方向を決める判断は人が握っている。読者を誰に置くか。どの技術を選ぶか。何を公開し、何を公開しないか。そして最終的に、この記事を公開してよいかどうか。これらはAIに委ねず、人が決める設計にしている。

各担当の進め方も「いきなり完成品を出さず、ヒアリング → 提案 → 合意 → 実行の順で対話する」ことを共通ルールにしている。AIが勝手に走るのではなく、節目ごとに人が確認して合意する。これが、限られた時間でも品質と方向性を保つための骨組みになっている。

## 技術選定の裏側(技術担当者向け)

ここからは、開発担当の方に向けて技術的な判断を一段深く記す。

記事を外部のヘッドレスCMS(記事管理の専用サービス)ではなく、リポジトリ内のファイルとして管理しているのには理由がある。記事も設定もすべてリポジトリで完結するため、AIエージェントと会話しながら、そのまま執筆やレビューができる。原稿がクラウド上の管理画面ではなく手元のファイルにあることが、この協働スタイルの前提になっている。

構成の要点は次のとおり。

| 項目 | 採用 | 理由 |
|---|---|---|
| フレームワーク | Astro(静的出力) | ビルドが速く、静的配信で実装自体も見せられる |
| 記事フォーマット | MDX | 通常の文章に加え、必要なら部品を埋め込める |
| コンテンツ管理 | Git ベース(外部CMSなし) | AIと会話しながら執筆・レビューできる |
| スタイル | 素のCSS(CSS変数) | 依存とビルドコストを増やさない |
| ホスティング | Vercel(静的) | 追加設定なしで無料公開できる |

一貫しているのは「シンプルで速く。過剰な抽象化や不要な依存追加はしない」という方針だ。ポートフォリオである以上、コードそのものも見られる前提で、読みやすく軽い構成を保っている。技術を増やすことではなく、目的に対して必要十分に絞ることを選んだ、ということだ。

## まとめ

このブログは、工程ごとに役割を分けたAIエージェントと対話しながら立ち上げた。要点は3つ。

- 幅広い工程を、担当の違うAIに分けて品質を保った
- たたき台と手を動かす作業はAI、方向を決める判断は人、と役割を分けた
- 節目ごとに人が確認して合意する進め方で、限られた時間に対応した

AIを使う開発は、丸投げでも全部手作業でもない。任せる部分と判断する部分を設計することが要になる。同じような進め方で開発を任せてみたい方は、お問い合わせからご相談いただきたい。
